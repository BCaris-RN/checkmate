# Checkmate Revamp — Work Orders

**Date:** 2026-08-26
**Goal:** make it feel better than chess.com and Duolingo chess, keep GitHub delivery, add a real download.
**Tier:** X (structural — touches presentation layer across the app)

---

## Assessment

The engine is not the problem. `match_models.dart` (1,167 lines) and `match_controller.dart` (981) carry real rules, LAN transport, hot-seat, replay export, and analytics. Platform-conditional imports are done properly with the io/web/stub pattern. Tests, CI, design tokens, and governance scripts are all in place, with a live remote at `github.com/BCaris-RN/checkmate`.

**The gap is entirely presentation.** Four specifics, all measured:

| Finding | Evidence | Consequence |
|---|---|---|
| No art | `assets/` holds 8 files, all icons and favicons | Six named themes can only be colour swaps |
| No motion | **0** `AnimationController` in `lib/` | Pieces teleport. This is the single biggest feel gap against chess.com |
| Thin design system | 4 colours, 4 font sizes in `design_tokens.g.dart` | A document palette, not a game palette |
| Monolithic UI | `match_screen.dart` is 1,237 lines | Any redesign fights the file |

**What already exists that helps:** GitHub Actions already builds a Windows release artifact, so "downloadable" is half-solved. `SEMANTIC_BUNDLE.txt` (6 MB) is current and ready for grounded reference.

# WO-R1 — Art direction and asset production
**Owner:** Gemini Pro · **Lane:** Research / Recon · **Tier:** X

### Scope
`assets/` and a written spec. **No code.**

### Deliverables

**1. Motion language spec.** The thing that separates a good chess app from a board renderer. Define, with durations and curves:
- piece pickup (lift, shadow spread)
- piece glide to destination
- capture (the taken piece's exit)
- illegal move rejection
- check alert on the king square
- checkmate resolution
- board flip between turns (this app is hot-seat, so the flip is a signature moment — chess.com barely has an equivalent)

**2. Board and piece system for the six existing themes** — Chrome Vanguard, Crystal Vault, Gilded Court, Carbon Night, Obsidian Relic, Aurora Myth. Per theme: light square, dark square, board edge, last-move highlight, legal-move dot, check glow, and the piece treatment.

**3. Piece art**, 12 pieces per theme (6 types × 2 colours). Must read clearly at **44 px** — this is played on a phone passed between two people. Vector-friendly, flat or 2.5D, no photoreal.

**4. Expanded design tokens** as a JSON block mapping onto the existing `design_tokens.g.dart` structure: full colour ramps, elevation, motion durations, motion curves.

The concrete palettes, asset names, QA images, and handoff block are specified in `docs/WO-R1-art-prompts.md`.

### Constraints
- Legibility at 44 px beats beauty at 512 px. Test every piece small.
- Two players share one phone and pass it back and forth. Both orientations must read well.
- A nine-year-old is one of the two players. Clarity over sophistication.
- Do not redesign the rules, the flow, or the information architecture.

### Do not touch
`lib/`, `test/`, `pubspec.yaml`, anything outside `assets/` and the spec document.

# WO-R2 — Animation layer and presentation refactor
**Owner:** Codex Cloud · **Lane:** Build · **Tier:** X
**Repo:** `github.com/BCaris-RN/checkmate` · **Branch:** `codex/revamp-motion-art` off `main`

### Scope
`lib/features/match/presentation/`, `lib/core/theme/`, `lib/core/tokens/`

### Deliverables

**1. Extract the monolith.** `match_screen.dart` is 1,237 lines. Split into `board/` (board, square, piece, coordinates), `controls/` (turn banner, action bar, timer), and a slim `match_screen.dart` that composes them. Behaviour identical — this is a pure structural move and every existing test must still pass untouched.

**2. Add the animation layer.** There are currently zero `AnimationController`s in the codebase. Implement against WO-R1's motion spec:
- animated piece movement between squares, not rebuild-and-reposition
- capture animation
- check and checkmate feedback
- board flip transition on pass-device
- illegal move rejection

Use implicit animations where they suffice; reach for explicit controllers only where the timing needs coordinating.

The exact motion timings, state model, reduced-motion behaviour, and manual QA matrix are specified in `docs/WO-R1-motion-spec.md`.

**3. Wire the asset pipeline.** Load theme piece art from `assets/`, with the current glyph rendering as fallback when a theme has no art yet. Declare assets in `pubspec.yaml`.

**4. Widen the tokens.** Extend `design_tokens.g.dart` from WO-R1's JSON. Keep the existing class shape so `design_token_guard.py` still passes.

### Constraints
- **Every existing test must pass unchanged.** Do not edit tests to accommodate the refactor. A test that needs changing means behaviour changed, which is out of scope.
- `flutter analyze` clean.
- `python scripts/design_token_guard.py --root .` must pass — no raw hex, no off-scale type.
- Animations must be disable-able. Respect `MediaQuery.disableAnimations`.
- Target 60fps on a mid-range Android phone. Profile before claiming it.

### Do not touch
`match_models.dart`, `match_controller.dart`, `match_transport*`, `match_storage.dart`. The engine is correct — this work order is presentation only.

Exception: read-only inspection of these files is expected. Code edits are out of scope unless a presentation bug exposes a previously unknown engine defect, in which case stop and report before changing engine files.

### Return block
Report `Status`, `Changed`, `Tests` (command and result), `Deviations`, `Untested`, `Next`. `Deviations` and `Untested` are mandatory; "none" is valid, blank is not.

# WO-R4 — Downloadable build
**Owner:** Operator · **Lane:** Publication · **Deferred until R1–R2 land**

GitHub Actions already produces a Windows release artifact, so this is packaging rather than building. `cp_super_stack_installer.iss` (Inno Setup) already exists in `skill_set` and is the starting point. Android APK via the same workflow is the second target — it is the platform the game is actually played on.

Ship order: **web (already live) → Android → Windows installer.**

WO-R4 does not start until:

- WO-R2 is merged or a release candidate branch is explicitly named.
- `flutter analyze` passes.
- `flutter test` passes.
- Design token guard passes.
- A human has played a full hot-seat game on an Android phone.

Expected artifacts:

- Web: existing GitHub Pages deployment remains the fastest trial surface.
- Android: debug APK first for device feel, release APK only after signing path is confirmed by the operator.
- Windows: installer based on the existing Inno Setup pattern from `skill_set`, but adapted to this app name and output path.

## Done definition

The revamp branch is ready for review when all of these are true:

- Three instruction docs are complete and committed.
- R1 assets exist for at least Carbon Night, or the PR explicitly says art is still pending.
- Presentation refactor keeps existing tests unchanged.
- Motion respects reduced-motion settings.
- Missing art falls back to glyph rendering.
- Piece image assets are transparent 2.5D/3D sprites only. Board squares remain
  in the board renderer and must not be baked into piece PNGs.
- Pawns promote through an explicit player choice among queen, rook, bishop,
  and knight.
- When either side is reduced to a lone king, the app shows a 21-move counter
  and declares a draw when it expires.
- Test results are reported with command and result.
- Deviations and untested areas are explicitly listed.
